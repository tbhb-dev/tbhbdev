The `actions_runner_pool` role runs a pool of ephemeral GitHub Actions runners on rootless Docker, one job per start of each slot's `systemd` user unit. `meta/argument_specs.yml` documents its options.

## Slot lifecycle

Each start of `actions-runner@N.service` has two phases, and `systemd` joins them, not a shell. Both phases are short linear scripts, without a wait on a background child and without a trap that cleans up. They share `actions-runner-slot-lib.sh`, which loads the settings and makes each API call. Its functions also request and revoke the installation token.

The start phase, `actions-runner-slot`, is the unit's `ExecStart=`. Its steps, in order:

1. Checks the settings, the token file, and the state directory. Next it prepares the Docker daemon. It exits 75 when the daemon's data root has less free space than `actions_runner_pool_min_free`, before any credential exists. It pulls the pinned image if it's missing and removes a container that a killed run left behind. Last, it creates the slot's own network if that doesn't exist.
2. Exits 0 after a stop signal, before any credential exists.
3. Runs `actions-runner-slot-stop --pending` when an earlier start's cleanup is pending (see invariant 6). It exits 75 unless that cleanup resolved, and then exits 0 after a stop signal.
4. Reads the App's key with `op read` and signs a JSON Web Token (JWT) with it, then trades the JWT for an installation token. See How `op` reads the key.
5. Deletes this slot's offline, idle runners (see invariant 5).
6. Requests a single-use runner configuration. It records the runner's ID and the container's name, neither of them secret, as the slot's pending cleanup in `pending` in the unit's `StateDirectory=`.
7. Revokes the installation token, and exits 75 without a job unless GitHub confirmed the revocation (see invariant 3).
8. Exits 0 after a stop signal.
9. Replaces itself, through `exec`, with `docker run --rm --sig-proxy=true` and a container named `actions-runner-slot-N`. The runner configuration reaches the container's standard input through process substitution.

After the `exec`, the docker client is the unit's main process, and no shell runs beside it. Its exit status, the container's, decides the unit's result, but no exit status stops the restarts. A rate limit or a transient error exits 75 at once. For a rate limit, a `rate-limited` log line comes first, with its kind, primary or secondary, and any Retry-After value. Then `RestartSec=`, `RestartSteps=`, and `RestartMaxDelaySec=` set the delay before the next try. That delay starts at 10 seconds and grows by a factor of about two up to 15 minutes, which allows about ten starts in the first hour.

Configuration errors stop the restarts through the unit's `ExecCondition=` line instead, which runs `actions-runner-slot --condition` before each start. It checks the settings, the token file, and the state directory, and exits 78 on any error. It also exits 78 while the state directory holds a `config-error` marker that's newer than both `pool.env` and the token file. The start phase leaves that marker, and exits 78, when GitHub refuses with a 401, with a 403 that isn't a rate limit and whose body is a GitHub error, or with a 404 for the installation or the runner group. Any other 403 exits 75 without the marker. After a condition exit from 1 to 254, `systemd` skips the start. The unit goes inactive with `ConditionResult=no`, and `Restart=` doesn't fire, so the operator's next start retries it. A changed `pool.env` or token file retires the marker, and so does removing it. The container never runs that check and can't write the marker, so its exit status can't stop the restarts. That's also why the unit has no `RestartPreventExitStatus=`. On `systemd` 259 that setting reads the main process's status, the container's after the `exec`. An `ExecStartPre=` failure doesn't trigger it either.

The stop phase, `actions-runner-slot-stop`, comes from the first `ExecStopPost=` line. Its steps, in order:

1. Takes the slot's lock without waiting (see invariant 6).
2. Classifies how the start ended, from `systemd`'s values and from whether a stop or restart job for the unit is running, which `systemctl --user list-jobs` shows. The start's outcome is `clean` after an exit 0 that no one requested a stop for. It's `stopped` after a requested stop, when the main process exited 0, 129, 130, or 143, or died of `SIGHUP`, `SIGINT`, or `SIGTERM`. It's `config-error` when the condition check skipped the start, and `failed` otherwise.
3. Removes the `actions-runner-slot-N` container with a bounded `docker rm --force`, which also stops a container that still runs.
4. Deletes the registration when the pending cleanup contains a runner ID and the container no longer exists. For that it requests a fresh installation token, sends the DELETE request, and then revokes that token. After a connection failure, a rate limit, or a server error, it retries the DELETE request, with at most four attempts within its deadline. A 2xx or a 404 resolves the registration. When the attempts run out, a `delete-failed` line logs the runner ID. A container that `docker rm` couldn't remove may still run a job. In that case the phase logs `delete-skipped` and leaves the registration alone.
5. Removes the pending cleanup once `docker rm` removed the container and the registration resolved, and prints one `job` line. That line contains the slot, the runner ID, the outcome, whether anyone requested a stop, whether a cleanup remains pending, and the `$SERVICE_RESULT`, `$EXIT_CODE`, `$EXIT_STATUS`, and `$INVOCATION_ID` values from `systemd`.

`SuccessExitStatus=129 130 143` lets a requested stop end clean even when the container passes on the stop signal's status. When no one requested a stop, the stop phase exits 1 after such a status, and `systemd` then counts the start as failed. It exits 75 while the container or the registration remains, or while another cleanup holds the lock, which also marks that start failed. Otherwise it exits 0. After both that command and the main process exit 0, the second `ExecStopPost=` line reset the restart counter. That keeps the delay at its shortest for clean jobs.

Handlers for `SIGINT`, `SIGTERM`, and `SIGHUP` record the first signal and ignore later signals, and the start phase reads that record at steps 2, 3, and 8. With `KillMode=mixed`, `systemd` sends the stop signal to the main process alone. A stop lets the start phase finish the calls in flight, and nothing cuts the runner configuration request or the revocation short. In the job phase the docker client is the unit's sole process. Rootless Docker runs the container under its own daemon's unit, and the stop phase removes it there.

Credentials stay in shell variables and pipes. `op` gets the 1Password token in its environment. `curl` reads the installation token or the JWT on its standard input as a configuration line. `docker run` reads the runner configuration from a pipe that process substitution opens, and avoids writing a temporary file for a here-document. Argument lists, files, and log lines never contain a credential.

The design keeps these invariants:

1. `systemd` runs cleanup, through `ExecStopPost=`, once per start. It runs the stop phase after the main process ends for any reason, such as a finished job, a failed or skipped start, a stop, a timeout, a crash, or a `SIGKILL`. With `Restart=`, the next start waits for the stop phase to end, and a manual start waits for it too. The pending cleanup in the unit's state directory passes the runner ID and the container's name from one phase to the other.
2. Each token's DELETE requests come before its revocation. In the start phase, the token serves the stale runners' DELETE requests and the runner configuration request, and its revocation comes last. Any failure after the token request exits through `die`, which revokes the token. In the stop phase, the token serves the registration's DELETE requests, and its revocation comes last.
3. Each token gets at most one revocation request, and no token exists while a job runs. `revoke_token` forgets the token before its single request, with no retry. It confirms revocation on a 2xx, 401, or 404 response. A 401 or 404 means the token is already invalid. Before the `exec`, the start phase revokes its token, and a start whose revocation wasn't confirmed never runs a job. After a timeout, a 429, or a 5xx there, it logs `revoke-failed` and exits 75 without the `exec`, and the stop phase deletes the registration as usual, with a fresh token of its own. The shell that ran the start phase kept the unconfirmed token. No container had it. It expires within the hour on its own, so later starts don't wait for it. The stop phase waits for the main process to exit. It removes the container first and waits for the container to disappear before requesting a token. A token that another failed revocation or a `SIGKILL` left unrevoked expires the same way.
4. Each phase's stop latency has a bound, and the unit's `TimeoutStopSec=` outlasts both. `actions_runner_pool_cleanup_seconds` sets the stop budget, 120 seconds, and `TimeoutStopSec=` adds 15 to it. Before the first check, a stop waits for the current preflight call and the calls after it. Each `docker` call there ends within 25 seconds, and the image pull within 605. A `SIGKILL` at the timeout loses nothing there, since no credential or registration exists yet. Past the first check, a pending cleanup ends within the budget, and the check right after it ends the run. From that check on, the start phase ends within 115 seconds. That covers `op read`, the token request, at most 30 seconds of reconcile plus the call in progress, the runner configuration request, and the revocation. Both phases refuse a budget under that bound, which exceeds the stop phase's own least of 105 seconds. In the job phase, the docker client passes the `SIGTERM` to the container, and the runner shuts down at its own pace. If that outlasts `TimeoutStopSec=`, `systemd` sends `SIGKILL` to the docker client, and the stop phase removes the container. A stop that lands between step 8 and the container's start, inside the docker client's own startup, can lose its signal and ends that way too. The stop phase ends within the budget by its deadline. `systemd` applies `TimeoutStopSec=` to each `ExecStopPost=` command. After it, `systemd` sends `SIGTERM`, then `SIGKILL` after another `TimeoutStopSec=`.
5. The next start repairs a crash. A power loss, or a `SIGKILL` of the stop phase, can leave a registration behind. Each start lists the organization's runners after it gets the token and before it requests a runner configuration. It deletes every offline, idle runner whose name matches `<prefix>-<host alias>-<slot>-<8 hex digits>` for its own slot. Prefixes can't contain a hyphen, the slot is all digits, and the random part has a fixed length. A name yields a unique prefix, host alias, and slot, and a slot can't match another slot's or another pool's runner. The preflight also removes any container labeled with the slot.
6. A pending cleanup stays in place until it resolves. The start phase records it after the runner configuration response gives the runner ID and before it extracts the encoded configuration, as `pending` in `~/.local/state/actions-runner-slot-N`, the unit's `StateDirectory=`, which keeps it across a stop and a reboot. A `SIGKILL` between the registration and that record doesn't leave a pending cleanup for the timer to act on, and the next start's reconcile deletes the registration. A cleanup waits for container removal and the registration's DELETE to resolve before removing it, so a failed `docker rm` or DELETE leaves it in place. The next start's step 3 retries it, and so do the next stop phase and `actions-runner-cleanup@N.service`, and none of them starts a job. A per-slot timer runs that service once every five minutes. For a slot within the slot count, the run exits 0 and doesn't print anything in two cases: nothing is pending, or the slot unit is active, activating, or deactivating and the lock was free. A slot waiting for a job keeps the pending cleanup its start recorded until its own stop phase resolves it. Finding the lock held still logs `cleanup-busy`, and a slot beyond the slot count still logs `cleanup-deferred` while its unit is active. The service runs `actions-runner-slot-stop --retry` and nothing else. It ends within the stop budget and never starts the slot unit. A manual `systemctl stop` doesn't fire `Restart=`, so after one the timer removes a container that `docker rm` couldn't remove during the stop. Whichever path runs the cleanup takes an `flock` on `lock` in the state directory without waiting, and one that finds it held leaves the work to the holder. While it holds the lock, `--retry` requires the slot unit to be inactive or failed, so never beside its start phase, job, or stop phase, which `systemd` already orders among themselves. A start that begins after that check finds the pending cleanup at step 3 and exits 75, because the retry holds the lock. No start records a new cleanup, or runs a container, before the retry has finished. A slot beyond the slot count keeps its timer, which removes that slot's leftovers (see Leftovers).

This behavior needs `systemd` 254 or later, for `RestartSteps=` and `RestartMaxDelaySec=`. The Molecule scenario checks the rest on the image's own `systemd` with transient units. `ExecStopPost=` runs after a `SIGKILL` and sees the result in its environment, and `TimeoutStopSec=` ends it. Both a restart and a manual start wait for it. With `Restart=always` set, an `ExecCondition=` exit of 78 skips the start without a restart, and `ExecStopPost=` still runs and sees `exec-condition`. The slot unit cases check the condition and the cleanup timer on the installed units, and that `list-jobs` shows a stop job during a requested stop and omits it otherwise.

## How `op` reads the key

`actions_runner_pool_op_auth` selects the credential that `op read` uses. The default, `service_account`, passes the token file's content as `OP_SERVICE_ACCOUNT_TOKEN`. With `connect`, the token file holds a 1Password Connect token. `op read` gets it as `OP_CONNECT_TOKEN`, with `OP_CONNECT_HOST` set to the Connect server and no service-account variable. Either way, the key reference comes from `actions_runner_pool_op_key_vault`, `_item` and `_field`, and the slot clears the token variable once `op read` returns.

- The Connect host is `https://op-connect.<MagicDNS suffix>`, the full name of `svc:op-connect`. The role reads the suffix from `tailscale status --json` on the host, as `host_telemetry` does. It then writes the URL to `pool.env`. Renaming the `Tailscale` network doesn't require a change in git. `actions_runner_pool_op_connect_host` overrides it. The slots don't call `tailscale` themselves: that call would add to the start and stop bounds, and the default budget has no room for it.
- With `connect`, the egress table accepts TCP port 443 to the addresses of the Connect host, ahead of its drops for the private, carrier-grade Network Address Translation (NAT), and unique local ranges, because the host is a `Tailscale` service inside those ranges. The role resolves the name with `getent ahosts` on the host at apply time and fails when it resolves to nothing. The table gets one rule for the IPv4 addresses and one for the IPv6 addresses, if that address family resolved. With `service_account`, the table has no such rule.
- The token file is mode 0600 with `connect` and 0400 with `service_account`, owned by the service user. The slots refuse any other mode. The role reads it from `actions_runner_pool_op_token_ref` (next bullet). With `connect`, the role fails when the file is missing, before it enables or starts any slot, and the message gives the file's path. If the file goes missing later, a slot's `op read` fails and its API status reads `op`.
- With `connect`, the role can write the token file itself. Set `actions_runner_pool_op_token_ref` to the token's `op://` reference, such as `host-host-a / runner-access-token / token`. The role runs `actions_runner_pool_op_token_lookup_command` there, with the reference as its argument. The file belongs to the service user with mode 0600, and the role rewrites it if the token differs and skips it otherwise. The task hides the token from the log and the diff, and check mode skips it. With the reference empty, the operator places the file. The role skips the lookup when the file already exists with content, so an operator script can place it. To rotate the token, replace or delete the file before a run.
- Set `actions_runner_pool_op_token_file` to its own path, such as `.config/actions-runner/op-connect-token`, when you switch a host to `connect`.
- The Connect token should have read access to the vault that holds the key and no other vault. It has no expiry. A leaked token works until `op connect token delete` removes it.

## Job-started hook

`actions_runner_pool_job_dir` and `actions_runner_pool_job_started_hook` add a job-started hook to every job. Both are empty by default. Something other than this role fills the job directory, a path under the service user's home. The start phase adds `--volume <directory>:/etc/actions-runner/job:ro` and `--env ACTIONS_RUNNER_HOOK_JOB_STARTED=/etc/actions-runner/job/<hook>` to the job's `docker run`. The runner then runs the hook before the job's first step, and a nonzero exit fails the job. Hook names must end in `.sh`, `.ps1`, or `.js`. Jobs get a protected mount for the hook. Whatever the hook calls has to be in the image, since the hook runs there. A missing hook file makes the settings check exit 78, and the unit's `--condition` runs that check before each start. No slot starts a job without the hook that the settings name. With the settings empty, the `docker run` is unchanged.

`actions_runner_pool_job_secrets_dir` adds secret files for the hook, empty by default. It needs the job directory and the hook, and their paths must not overlap once `realpath` resolves them. The files total at most 16 KiB. The settings check exits 78 on a breach of any of these, and for an empty hook. No container mounts the directory.

Before the exec, the start phase makes a named pipe in the state directory, mode 0666. It also starts a background writer, `{ tar --create ... | base64; } >pipe &`, whose redirect opens the pipe before `tar` reads a file. The job container mounts the pipe at `/etc/actions-runner/job-secrets` with the `:ro` flag and gets an empty `tmpfs` at `/run/job-secrets`, owned by 1001 with mode 0700. The writer sends base64 of the tar stream, because a shell variable can hold that text and can't hold the zero bytes of a tar stream. Its size stays under the pipe buffer. Once the hook opens the pipe, the writer writes everything and exits. A reader after that gets an empty pipe and blocks. Each start recreates the pipe. A writer that never gets a reader waits until the container ends, so a hook that never opens the pipe leaves nothing to read.

## The slot's Docker daemon

### How it works

With `actions_runner_pool_dind_image` set, each slot runs its own Docker daemon beside the job. At step 1, the start phase removes and inspects the three slot volumes. If a volume still exists, it removes containers that reference it and retries the volume removal once. If the volume remains, a helper in the image for that daemon empties it as root with networking off. After creating the volumes, the helper checks that all three are empty. The start exits 75 before runner registration if it fails to prepare empty volumes.

Next the start phase launches the daemon, a `docker:dind` container named `actions-runner-dind-N`, on the slot's network and waits until it answers. Rootless Docker confines `--privileged` to the service user's isolated environment. Traffic from the slot's daemon leaves as the service user, and the egress table applies to the containers a job starts through it.

- `actions-runner-dind-N` holds the daemon's socket.
- `actions-runner-work-N` is a volume owned by 1001, the runner's user. Both the job and the daemon mount it at `/home/runner/_work`, so paths under the workspace mean the same files to both.
- `actions-runner-tmp-N` is a volume both mount at `/tmp`, for actions that bind-mount files they write there.

`actions_runner_pool_work_on_disk` defaults to `false`, which keeps work and shared `/tmp` in `tmpfs` volumes sized by `actions_runner_pool_work_size`. Without a slot daemon, work is a `--tmpfs` mount of that size. `tmpfs` pages count against the memory limit.

With `actions_runner_pool_work_on_disk: true`, which requires `actions_runner_pool_dind_image`, the start creates both as plain local volumes. The root helper sets work to 1001:1001 mode 0700 and shared `/tmp` to mode 1777. If Docker keeps an existing volume after the removal retry, that volume retains its storage options.

On disk, a job's work and `/tmp` files stay on the disk of the runner VM for the job's duration. That includes actions/checkout's git-credentials configuration under `_work/_temp`, which holds the job's token. The slot's stop phase removes the files when the job ends, and the next start removes any that a killed stop phase left behind, but removal doesn't overwrite the freed blocks, and neither a CI VM nor its host encrypts the disk, where each CI VM is a plain logical volume.

A runaway job can fill the Docker storage for its slot. That storage is a loop file of fixed size, so the job can't fill the root file system of the VM with it.

Reserve it for hosts with a dedicated disk.

Each job container mounts all three and gets `DOCKER_HOST` for the socket. With its `label!=actions-runner-pool.slot` filter, the prune unit never removes them.

The daemon listens on that Unix socket and has no network listener. The runner joins `container:actions-runner-dind-N`, sharing the sidecar's isolated network and resolver, so a container started through `DOCKER_HOST` with a port published on `127.0.0.1` answers on the job's `127.0.0.1`. The sidecar stays on the slot bridge with the configured DNS servers and inter-container traffic turned off. The egress table applies to both. Without a slot daemon, the runner joins the slot bridge directly and gets the configured DNS servers through `--dns`.

During cleanup, the stop phase removes the daemon and volumes for slots within the slot count. Both the start phase's `--pending` run and the cleanup timer's `--retry` run leave them alone. A start creates them at its step 1, before its step 3 takes the lock, so a removal from that `--pending` run, or from a `--retry` that checked the unit before the start began, took them from under the job. Docker then created a plain, root-owned work volume for the job when the job started, and the job failed before its first step. The stop phase removes them with these calls:

```bash
docker rm --force -- actions-runner-dind-N
docker volume rm --force -- actions-runner-dind-N actions-runner-work-N actions-runner-tmp-N
```

### Leftovers

If removal fails during the stop phase, or if `systemd` kills that phase before removal, the daemon and the volumes stay until the slot starts again. That start's step 1 removes every container labeled with the slot and recreates the volumes. A slot beyond the slot count never starts again, so for such a slot the cleanup timer's `--retry` removes them. `pool.env` passes the slot count as `ACTIONS_RUNNER_POOL_SLOTS`. Under the slot's lock, once any pending cleanup has run, `--retry` checks two conditions. First, the slot unit must be inactive or failed. Second, `systemctl --user is-enabled` must answer `disabled`. If both checks pass, it removes every container and volume labeled with the slot and log one `leftovers-removed` line with the counts. Any other answer, `enabled-runtime` or an error among them, skips the removal and logs `leftovers-skipped`. An apply that raises the slot count enables a slot before it starts it, so no start can begin beside the removal. When a removal fails, the run exits 75, and the next timer run tries again. A slot that was never within the slot count has no timer, and never had a daemon.
